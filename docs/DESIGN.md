# 설계 노트

이 문서는 이 도구의 구조, 각 선택의 이유, 확인된 한계를 정리한 설계 노트입니다.

## 1. 왜 세 단계로 나눴나

| 단계 | 하는 일 | 밖으로 나가는 것 | 실패해도 |
|---|---|---|---|
| 색인·로컬 보강 | 사진 앱 내부 정보와 공개 Vision 분류기·OCR 결과를 `index/cards.sqlite`로 옮김 | 없음 | 질문 단계가 시작되지 않음 |
| 질문 | Claude가 표를 도구로 검색 | 질문·요약·도구 결과 글자 | 후보가 줄 뿐 색인은 그대로 |
| 캡션(선택) | 미리보기를 Gemini로 보내 한 줄 설명 | 미리보기 JPEG | 없어도 질문 단계 동작 |

한 덩어리로 만들면 사진을 보내는 단계와 글자만 보내는 단계가 섞입니다. 그러면
"이 질문에 사진이 나갔나?"를 코드에서 확인하기 어려워집니다. 단계를 나누면
`photo_ask/agent.py:3`처럼 각 단계가 무엇을 보내는지 한 곳에서 확인됩니다.

또 하나는 실패 격리입니다. 캡션이 0장이어도 질문은 됩니다. 요약과 도구가
"캡션이 없다"고 알려 주고(`photo_ask/cards_query.py:677`), 장면 라벨·Vision 라벨·사진 속 글자로
찾습니다. 캡션은 사진 내용 단서를 더하는 선택 재료이지 전제가 아닙니다(캡션으로 정확도가 얼마나 오르는지는 재지 않았습니다).

## 2. 왜 분류를 먼저 확정하지 않고 도구로 찾게 했나

질문을 미리 정한 분류표(예: 장소·음식·사람)로 나눠 두면, 사용자가 그 표에 없는 말을 할 때 바로 막힙니다.
"저번달쯤 강원도 카페에서 찍은 사진"은 날짜·장소·장소 유형이 한 문장에 섞여 있고,
"양식"은 사진에 찍힌 물체가 아니라 추정입니다. 질문마다 필요한 축이 다릅니다.

그래서 모델에게 **도구를 주고 스스로 고르게** 했습니다. 도구는 세 개입니다.

- `search_cards`: 조건을 모두 만족하는 카드와 분포
- `stats`: 한 축으로 센 건수
- `list_vocab`: 인덱스에 실제 있는 낱말

모델이 인덱스에 없는 낱말을 넣으면 조용히 빼지 않고 `unknown`에 비슷한 후보를 적어 돌려줍니다
(`photo_ask/cards_query.py:138`). 다만 결과가 되는 조건은 필터 종류마다 다릅니다.

- `labels_all`: 하나라도 없으면 0건입니다(모든 낱말이 없을 때와 일부만 없을 때 모두).
- `labels_any`·`vision_labels_any`·`states`·`cities`: 맞는 낱말만으로 찾습니다. 하나도 못 맞히면 0건이고,
  없는 낱말은 `unknown`에 남습니다.
- `exclude_labels`: 없는 낱말은 아무 효과 없이 무시합니다.

0건일 때는 한 번에 하나만 넓힙니다. 라벨 → 장소 → 날짜 순서이고, 최대 4회입니다.
사용자가 말한 시기(「저번달」)는 가장 나중에 넓힙니다. 처음부터 넓히면 "저번달"이라고 답하면서
실제로는 1년치를 뒤진 결과가 나옵니다. 이 지시는 `photo_ask/agent.py:131`에 있습니다.
**「최대 4회」는 시스템 프롬프트의 지시일 뿐 코드가 강제하지 않습니다.** 코드는 0건 뒤 다시 찾은
횟수를 `widen_count`로 세기만 합니다(`photo_ask/agent.py:457`).

최종 후보가 50건을 넘으면 한 번 되묻도록 모델에 지시합니다(`photo_ask/agent.py:132`).
50건을 표에 다 보여 주면 사용자가 고를 수 없고, 그렇다고 임의로 20건만 자르면
"왜 이 사진은 없나"에 답할 수 없습니다. 그래서 breakdown에서 **실제로 갈리는 축** 하나를 골라
선택지마다 건수를 붙여 묻습니다. 이미 한 번 물었으면 다시 묻지 않습니다.
「가장 잘 나온」「글자 많은」처럼 순서가 답인 질문은 그 순서로 정렬해 답하고 되묻지 않는다는 것도
모델 지시입니다. 코드가 강제하는 것은 그중 하나뿐입니다 — 최종 결과가 50건을 넘고 정렬이
`date_desc`/`date_asc`이며 아직 되묻거나 자동 재요청하지 않았을 때, 코드가 한 번만 재요청을 붙입니다
(`photo_ask/agent.py:500-506`).

## 3. 겪은 문제와 해결

### ① 라벨과 캡션을 AND로 겹치면 결과가 크게 줄었다

"바다"를 장면 라벨과 캡션 양쪽에서 찾으면 둘 다 있는 사진만 남습니다. 캡션은 사진에만 있고
영상에는 없으며, 라벨이 없는 사진도 많습니다. 그래서 사진 내용 조건끼리만 묶는
`content_match`를 두고, 내용을 찾을 때는 `any`를 쓰게 했습니다(`photo_ask/cards_query.py:238`).
날짜·장소·요리 국적 같은 다른 조건은 그대로 AND입니다.

포기한 것: `any`는 조건을 느슨하게 하므로 관련 없는 사진이 섞일 수 있습니다.
대신 분포를 함께 보여 주고 50건 규칙으로 되묻습니다.

### ② 한국어 2음절 낱말이 FTS5 trigram에서 0건이었다

"바다"처럼 두 글자 낱말은 trigram 토크나이저가 못 찾습니다. 세 글자부터 잡힙니다.
그래서 `cards_fts`는 `unicode61`로 만들고(`photo_ask/cards_schema.py:59`),
부분 일치는 LIKE로도 함께 겁니다. 정렬은 `text_like`가 있을 때만 bm25를 씁니다.
trigram을 버린 대신 아주 긴 문장의 부분 일치는 LIKE가 느립니다. 수만 줄 규모에서 LIKE 부분 일치가
느린지는 재지 않았습니다. 수십만 장이 되면 다시 재야 합니다.

### ③ osxphotos가 잠기지 않은 DB 원본을 열었다

osxphotos는 DB가 잠겨 있지 않으면 보관함 원본을 그대로 엽니다. 그러면 SQLite 연결이
원본 파일에 닿습니다. 그래서 우리가 먼저 `Photos.sqlite`와 `search/*.sqlite`를 임시 폴더로
복사하고, 복사본만 엽니다(`photo_ask/library_copy.py:4`). osxphotos가 실제로 연 파일이
보관함 안이면 즉시 중단하는 검사도 둡니다(`index/build_index.py:323`).

포기한 것: 색인 한 번에 보관함 DB 크기만큼 임시 디스크를 씁니다. 복사 시간도 듭니다.

### ④ 백그라운드 파이썬이 보관함 파일을 열면 오류 없이 멈췄다

웹 서버나 `launchd`로 띄운 파이썬이 보관함 안 미리보기를 열면, 권한 때문에 예외가 아니라
**멈춤**이 됩니다. 그래서 웹 서버는 보관함을 직접 열지 않고, 터미널에서 미리 만든
`index/previews/<uuid>.jpeg` 캐시만 읽습니다(`photo_ask/preview_cache.py:3`).
캐시는 APFS 복제(clonefile)를 먼저 시도하고, 복제가 안 되면(다른 볼륨이거나 clonefile 실패)
보통 복사로 넘어갑니다(`photo_ask/preview_cache.py:111`). 같은 APFS 볼륨이면 디스크를 거의 쓰지 않습니다.

포기한 것: 사진을 추가한 뒤 `sync_previews.py`를 다시 돌리기 전까지 웹 화면에 안 보입니다.
원본 화질도 아닙니다.

### ⑤ 모델마다 요리 국적 판단이 갈렸다

"양식"을 물었을 때 어떤 응답은 파스타를 양식, 어떤 응답은 기타로 썼습니다. 자유 문장으로 두면
검색 필터가 흔들립니다. 그래서 캡션 응답 스키마에 고정 목록을 넣고(`photo_ask/caption.py:23`),
목록 밖 값은 저장 전에 거부합니다(`photo_ask/caption.py:128`). 질문 단계도 같은 목록을
`cuisine` 필터의 enum으로 씁니다(`photo_ask/agent.py:50`).

포기한 것: 목록에 없는 요리(예: 지중해식)는 "기타"로 뭉칩니다. 목록을 늘리면 모델이 고르는
폭이 넓어져 다시 흔들릴 수 있어, 지금은 7개로 고정했습니다.

### ⑥ 예산 상한과 호출 기록을 처음부터 뒀다

질문 한 번에 도구 호출이 여러 번 나가고, 캡션은 사진 수만큼 요청이 나갑니다. 나중에 붙이면
"지난달에 얼마 썼나"를 알 수 없습니다. 그래서 첫 호출부터 `logs/llm.jsonl`에 한 줄씩 남기고
(`photo_ask/llm_log.py:61`), 새 호출 전에 그때까지 기록된 비용으로 누적·질문당·캡션 상한을 검사합니다
(`photo_ask/config.py:22`, `photo_ask/config.py:41`). 이 검사는 이미 쓴 비용으로 하므로 진행 중인 호출이나
재시도가 있으면 상한을 조금 넘을 수 있고, 상한 자체도 가격표로 계산한 추정입니다. 모르는 모델 이름이 와도
가장 비싼 값으로 계산해서 과소 추정을 피합니다(`photo_ask/config.py:35-36`).

포기한 것: 기록 파일이 계속 커집니다. 지금은 줄 단위 append만 하고 회전하지 않습니다.

## 4. 측정하지 않은 것

- **찾은 사진의 정확도.** 정답 묶음을 만들어 재지 않았습니다. 상위 몇 건 안에 정답이 들어가는지 수치가 없습니다.
- **다른 도구와의 비교.** 사진 앱 자체 검색, 다른 사진 검색 도구와 같은 질문으로 비교하지 않았습니다.
- **다른 macOS 버전.** 시험 환경은 macOS 27.0.1 한 대뿐입니다. 다른 버전에서는 시험하지 않았고,
  내부 DB 형식이 바뀌면 깨질 수 있습니다.
- **큰 보관함에서의 속도.** 사진이 아주 많을 때 색인·검색 시간을 재지 않았습니다.
- **사진을 편집한 뒤의 캡션.** 캡션은 만들 때의 미리보기를 기준으로 하며, 사진을 편집해도 이미 만든
  캡션은 자동으로 갱신되지 않습니다.
